## Final-pin series: transactional sink, managed RX, shared-Owner qualification (2026-09-16)
- `DatagramSink` is transactional by construction: `acquire(peer, wire_len) -> Result<Option<Slot>, Error>` decides every fallible capacity question before the protocol is touched, `bytes_mut` is the only way to fill reserved storage, and `commit(self, len)` is infallible. Applied to CallerTable direct callers and group legs, the admission peer/leg paths, the `Vec` compatibility sink, the Compio Owner TX sink, and the benchmark sink. `OutputDrainReport` now carries `sink_outcome`, `sink_error_kind`, and `sink_rejections`, and a refused datagram is re-queued so it stays visible instead of vanishing. Adversarial tests cover exhausted/refused/success/commit/group/Owner-pool cases.
- **Managed multishot RX verified by execution on a qualified kernel** (`docs/results/managed-rx-verification.md`): `linux-image-7.0.0-31-generic` was booted under QEMU (TCG, `-cpu max`) since the dev host's `6.8.0-139-generic` rejects `IORING_REGISTER_PBUF_RING`. There, a `ManagedRequired` Owner attached with `rx_mode=ManagedMultishot`, delivered a legal datagram through the managed ring, counted a 4096-byte datagram as `truncated=1` (never parsed), and shut down quiescent (`in_flight=0`, pool `64/64`). The committed regression test `managed_multishot_delivers_and_counts_truncated_datagrams` passes on that kernel and self-skips where the substrate is absent. This closes the "managed RX actually used by the production Owner" gate; the remaining work is to run the existing qualification harness on a production kernel, not to build the datapath.
- Managed multishot RX: one persistent `recv_msg_multi` task per shared UDP socket feeding a fixed 256-entry preallocated ring; it is the socket's only consumer. `MSG_TRUNC` reporting is why the msg form is used: an oversized datagram is dropped and counted, never parsed short, which is what allows managed slots to be sized from the wire ceiling (1500 -> 2048 B; ring cost 512 KiB instead of 16 MiB). A stopped or errored task faults the Owner (`RxStreamFailed`). **Teardown rule:** cancelling the task is not enough — `shutdown_and_drain` stops and **awaits** the consumer on each side, because dropping the `JoinHandle` cancels without running the unwinding to completion and leaves the armed receive holding its leases (measured: 256 x 2048 B = 512 KiB, `docs/results/managed-rx-verification.md`).
- **Managed RX ownership rule (closure pass).** The ring owns the RX task's `JoinHandle`, so no strong `Rc` back to the ring may live **across the receive await**; holding one is the cycle `ManagedRxRing -> JoinHandle -> task future -> Rc<ManagedRxRing>`, which outlives the Owner and leaks the ring plus its entire provided-buffer pool. Passing `Weak` as the parameter is *not* sufficient — the upgrade has to be scoped, and it now is: the strong reference is taken inside a block that ends before `stream.next().await`, and the post-await path re-upgrades. The loop is generic over a step stream, so the regression test parks and drops the **production** function (`managed_rx_task_holds_no_strong_ring_across_the_receive_await`: while parked, `Rc::strong_count(&ring) == 1` and dropping the owner frees the ring immediately) rather than a stand-in. Measured under ASan/LSan on kernel 7.0.0-31: teardown returns every provided-buffer lease, no leak.
- **Capability is one observed fact, and it names all three substrate pieces.** `ManagedRxSubstrate` is `NotIoUring | BufferRingRegistrationFailed(errno) | MultishotRecvUnsupported | Available`, derived by `CompioProductionProfile::managed_rx_substrate()` from an observation of the exact runtime (`observe_production_runtime`), declared once through `Owner::set_rx_substrate`, and consumed by every attach. `RxModePolicy::ManagedRequired` attaches a managed consumer only on `Available`: it requires **io_uring AND a registered provided-buffer ring AND recvmsg multishot**, refuses when no substrate was observed, and reports the layer that actually failed instead of blaming `IORING_REGISTER_PBUF_RING` unconditionally. `ManagedPreferred` degrades visibly, and `ManagedRxQualification::managed_rx_active()` is the host-capability + selected-mode conjunction — a datapath statement, never a workload-level qualification.
- Owner coupling sealed: side fields private, `listener_mut`/`caller_mut` removed, `with_listener`/`with_caller` and side constructors test/bench-gated, production attach only through `listen`/`connect`.
- **TX failure domain (closure pass).** A failed `send_to` is classified by errno (with `ErrorKind` fallback) as `PeerLocal` (`EHOSTUNREACH`, `ENETUNREACH`, `ECONNREFUSED`, `ECONNRESET`, ...), `TransientLocal` (`ENOBUFS`, `EAGAIN`, `EINTR`, `ENOMEM`, `ETIMEDOUT`) or `OwnerStructural` (`EMSGSIZE` on our own sized datagram, `EBADF`, `EINVAL`, unrecognized). Only `OwnerStructural` — and an unexpected short UDP send — faults the Owner; `PeerLocal`/`TransientLocal` completions are counted, attributed on a bounded `TxFailureQueue` (`poll_tx_failures`), and **never retried inside the transport**, so one broken destination cannot stop healthy siblings on the shared socket. This is the boundary the ledger previously stated as "any completion error faults the Owner".
- **One operational predicate.** `Owner::is_operational()` (`fault().is_none() && !shutdown`) gates `listen`, `connect`, `DatagramSink::acquire` and `service`'s RX/maintenance/TX phases; `service` harvests faults *before* admitting anything, so a visit never admits work on behalf of a consumer that is already dead. `service` stays callable while faulted so completions can still be reaped and the Owner still reports truthfully.
- **`wait_for_activity` never consumes work.** It observes completion readiness (`TxEngine::poll_activity`/`completion_ready`) and registers wakers only: it never dequeues a completion, never returns a `TxPool` slot, and never advances accounting. `service` is the sole normal reaper and `max_completions` is authoritative, including `max_completions == 0` (zero reaping regardless of prior waits). Previously the wait path reaped one completion, which both broke the waiting/execution boundary and omitted that completion from the next visit's deltas.
- **One teardown deadline.** `shutdown_and_drain(timeout)` uses ONE absolute deadline for every phase (listener RX stop, caller RX stop, TX drain, lane signalling, lane joins). It reports quiescence only when every invariant is evaluated from state: both managed consumers joined, no staged lease, both rings empty, `tx_in_flight() == 0`, every lane joined, `tx_pool.free_count() == capacity()`. An RX worker that will not stop yields `false` with `OwnerFault::RxShutdownTimedOut { side }` instead of a fabricated success. The misleading synchronous `Owner::shutdown()` was deleted; `shutdown_and_drain` is the only teardown.
- Lifecycle maintenance is bounded by `max_actions` alone (`service_maintenance`), so a zero TX packet/byte allowance no longer suppresses caller-attempt expiration or listener idle reclaim; `CallerPool::poll_expirations_count_only` is the allocation-free path the Owner uses.
- **Shared-Owner qualification harness (`compio_shared_owner_qual`)** runs the production Owner as an external process against an independent receiver with an establishment barrier and an open-loop 8 Mbps source. **F, K and H are independent inputs** (`--fanout`, `--tx-lanes`, `--connect-cc`); no run derives K or H from F, and the harness respects the pool's bounded request queue by re-issuing refused connects. Results: `docs/results/qual-shared-owner-frontier.md`. Canonical fixed-K/fixed-H rows (K=256, H=64, one sender process): 1/10/100/150/200 all establish fully and reconcile delivery exactly (`core_total == pkt_sent`, `sec_a = 0`, `drain_ok=true`), and **600/600 and 1000/1000 both establish with 100 % of offered copies accepted** — retiring the earlier "600 cannot establish in one process" reading, which was a handshake-concurrency artifact of `max_in_flight = fanout`. At 600/1000 the one-core shard saturates at F x 8 Mbps offered load (pool 0/256 free, 257 in flight at the drain deadline, p99 source lateness 30 ms / 268 ms): establishment is established, **capacity is not claimed**. 1/10/100 establish and reconcile exactly; one Owner core saturates near 100 destinations (p99 source lateness 18.1 ms, 94 % of a core); 600/1000 did **not** establish in **one** sender process on this 6-CPU host; sharding the sender changes that: 2x100 = 200 reconcile exactly (`core_total == pkt_sent`, `sec_a=0`) and 4x150 = **600/600 established** with every shard draining to zero, but the single receiver process is then starved (44,700 lost DATA packets), so 600 clean delivery is receiver-capacity bound on this host and 1000 remains unestablished. Every row is `managed_rx=false`: this kernel rejects `IORING_REGISTER_PBUF_RING`, so the run is a raw-reader result and explicitly not a managed-RX qualification.
